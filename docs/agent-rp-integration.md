# RP Studio 1.4 与通用故事

此版本仍在开发。工程测试覆盖 Studio 的 UI、解析器和合同适配器；使用真实安装包完成跨插件原生验收后才发布。测试中的合成服务不证明真实模型写作质量或完整存档恢复成功。

## 事实审批与两层重新生成

本故事的事实审批默认关闭，使用 GM 保存的设置版本单独修改。开启后，普通回合先留下候选；候选不是 Database 当前事实。工作区展示当前事实与所选候选，支持“通过并继续”“重试事实”“自定义事实”和“取消本次候选”。自定义使用场景、事实、摘要和公开方向的表单，直接提交人类输入，已经执行的工具不重跑。待审时普通行动暂停，输入框文字保留。

“重新生成事实”使用被捕获的回合起点、玩家输入和固定工具证据，修改的是当前有效事实版本。仅最近一个合格普通回合可用；旧回执没有冻结基线时显示 LEGACY_BASELINE_UNAVAILABLE。审批策略由 owner 捕获；关闭开关不会自动批准已等待的候选。

“只重新写作”使用当前事实版本已有的完整冻结 composition，只请求 writer。它通过真实 owner 调度追加新的正文结果。原有回退、分支和正文草稿采用继续是独立操作。

操作编号在请求前生成。响应丢失后使用原编号重试，候选、选中项及随后编辑的文字不会被晚到响应替换。冷后从公开 pendingDecision 或 generation 恢复；“继续候选结算”只结算已暂存结果，GENERATION_NOT_STAGED 需要用户明确发起新的生成。批准事实与写作是两个阶段，写作失败保留已生效事实，使用原决定继续写作。

“继续审批结算”和“继续候选结算”整个端点均不请求模型，审批关闭时也不会自动写作。结算完成后明确点击“继续已批准事实的写作”。可确定的结算拒绝会保存失败并释放占用，重新决定使用新的操作编号和实际最新版本；取消候选不要求重新取得事实写权限。

新功能要求 GM 0.2 的 factReview/factRegeneration、Database 0.3 的 factReview，以及 RP 最后一步 0.4 的 narrativeRevisions，且对应方法真实存在。Context 0.3 与 Story Kit 0.2 分别提供有效材料与阅读稿消费；Loop 0.1 不变。旧插件按实际能力保留旧路径。

## 旧版路径与安装基线（1.3）

1.3 面向官方 DSH 0.2.1-rc.3，Node 24 构建。旧版 1.2 及其已证明的 rc.2 支持不变。新版统一入口的目标依赖如下；它们都是独立插件，不能从本仓历史快照代替安装。

| 项目 | 目标版本 | 在组合中的职责 |
| --- | --- | --- |
| RP Studio | 1.3.0 | 原生游玩、阅读与统一操作入口 |
| [RP GM](https://github.com/LiweiDonVee/dsh-rp-gm) | 0.1.0 | 通用开局、事实协议、合法分支/回退 |
| [Story Kit](https://github.com/LiweiDonVee/dsh-rp-story-kit) | 0.1.0 | 角色、persona、开场、内容包及恢复协调 |
| [RP Database](https://github.com/LiweiDonVee/dsh-rp-database) | 0.2.0 | 版本固定的多库、事实、文件资料与检索 |
| [RP Context](https://github.com/LiweiDonVee/dsh-rp-context) | 0.2.0 | 历史表示、选材与下一轮作者注；通用开局可选 |
| [RP 最后一步](https://github.com/LiweiDonVee/dsh-rp-last-step) | 0.3.0 | 正文、冻结输入、候选和合法采用 |
| [Loop Studio](https://github.com/LiweiDonVee/dsh-loop-studio) | 0.1.0，不变 | 既有主请求、选材、摘要、组装和正文模型路由 |

通用开局需要 GM、Database 和 RP 最后一步的对应能力。Story Kit 的角色库本身仍可单独使用。旧预设故事阅读不要求安装整套插件。缺少方法、版本或受限执行能力时，Studio 禁用对应动作并显示实际连接状况，不根据服务名字推测未来功能。

## 从角色与开场开始

在 RP 工作区的 Story Kit 原生入口导入或创建角色与玩家身份，选择不可变版本、开场和资料来源。导入脚本、未知扩展及示例对话不会自动成为系统指令或历史事件。内嵌世界书由用户明确交给 Database；内容包中的外来正文预设须在所属插件审阅后才可用于故事。

Story Kit 调用通用 GM 开局，不要求为每张角色卡编写 runtime 或注册预设。正式首轮由正常原生执行产生，所选开场经真实 rp_present 成为历史。Studio 通过 GM 的故事目录与绑定识别该故事；不从模型提示词猜测身份。旧 roster/bundle 识别继续保留。

## 当前状态与分支

“角色与剧情”显示 GM 服务返回的场景和事实。其真值仍在 Database，Studio 不另存一份世界状态；固定角色来源与当前事实也不混为一谈。

通用故事的“回退”定位最近普通事实回合之前的有效前缀，“分支”保留选定前缀；两者都会打开子故事并保留原故事。开场不会退到无效的空日志。通用 GM 的自动续写能力为 false，请直接发送下一条玩家行动。旧预设的回退、分支和自动续写保持原有路径。

回退也必须排除触发该回合的已入队玩家输入，保留此前已完成历史。若多条排队输入相互交织，无法用合法前缀隔离，会返回 ROLLBACK_UNAVAILABLE 且不创建子故事。成功回退后的冷继续只结算明确的新行动。

## 候选、采用、失败重试

在“沉浸阅读”展开“正文与材料”，读取当前正式正文版本。生成候选复用冻结材料，只请求正文阶段；手改当前正文不调用模型。未采用的候选不进入故事或 Context。先保存修改，再比较并采用；并发修改会返回版本冲突，编辑框保留未保存文字。

保存请求等待期间继续输入的文字也会保留，并以刚确认的持久版本继续保存；切换候选后，旧请求的响应不会抢回选择。

采用同时固定当前有效 NarrativeRef 和已预览的持久草稿版本。另一窗口修改同一草稿会得到 DRAFT_VERSION_CONFLICT，原故事不变，预览与编辑保留，需明确刷新和重新预览；不会按 ID 采用未读过的新文字。所属插件也会重新检查来源和下游工作。它通过合法原生维护回合替换正文 content，不重复事实或模型调用。宿主可能将这次无生成维护回合标记为 blocked；Studio 单独展示采用确认，保留宿主诊断，不把它编写成剧情中的失败。阅读器刷新到有效采用稿，旧 metadata 中的原稿不会覆盖新正文。

失败列表使用所属插件的 body-free 摘要。只有该行 canRetry 和会话 retryDispatch 都为 true，且没有正在运行的请求时才能重试。rendered 只代表阶段输出，不等于规范历史已接受。重试可能有一次主模型调度，再进入正文请求；不会重新结算事实、选材或组装模块。执行时仍会重新验证资格。

## 冻结材料与作者注

“查看当前正文材料”或回执的“查看该次材料”读取所属插件保存的精确输入，分别显示固定角色/身份来源、当时方向与事实回执、记录的候选池、历史表示、编译模块及实际模型。固定来源使用当时冻结的 storySnapshot；老回执没有该字段时明确显示未记录，不从今天的角色版本补造旧输入，也不虚构 token、检索轨迹或 reasoning。

作者注显示 pending、claimed 或 consumed 状态。编辑进入 Context 原生面板，由其处理 revision、认领和消费；Studio 不从 note.version 猜测整个 store revision。失败重试使用原冻结注，后来新写的注不能改变已捕获材料。多库绑定、来源版本、条目策略和文件索引进入 Database 原生面板管理。

## 三种可迁移内容

| 形式 | 用途 | 能否恢复完整故事 |
| --- | --- | --- |
| 内容包 | 分享角色、persona、开场、资料和审阅中的预设；在 Story Kit 组合/导入 | 否；目标环境生成新的内容 ID |
| 阅读稿 | Markdown / 纯文本，只导出当前有效采用正文 | 否 |
| 完整存档 | Story Kit 协调规范 Session 与各插件所需状态，精确保留 ID | 仅在目标环境全部依赖、来源和冷恢复验证通过后 |

完整存档导入先预检。RESTORE_ID_CONFLICT 不覆盖、不自动改名；pending 不是完成，保留任务 ID 并使用“继续恢复”。只有 owner 返回 complete 后才打开恢复的故事。模型凭据和本机 provider 配置需要在目标环境自行配置，不随文件复制。恢复工具不直接改写私有日志，也不重演历史工具。

若预检的 deferredChecks 含 LOOP_NODE_VALIDATION，supported:true 只表示支持条件暂存，尚不表示目标真实路由兼容。使用“暂存并验证目标路由”后，所属插件在恢复门禁下无 prompt 恢复 Agent，检查真实节点和控制能力，全部通过才能激活。失败继续保留 pending/failed 记录，不静默删路由、换模型或把暂存称为完成。存档保留宿主提供的 inheritedEventCount，不从相似历史猜继承数量；未安装 Context 的源环境明确保存 context:null。

导出、预检和恢复还分别要求 Story Kit 的 savedStoryExport、savedStoryPreview、savedStoryRestore 为 true，并存在对应方法；资料库可打开不代表恢复机制可用。当前已验证 rc.3 的跨环境头比较仅允许 delegationDepth 缺省与数值 0 等价，null、字符串、非零及其他头变化均不等价；原事件前缀仍须严格相等。Studio 转交原始数据，不自行放宽比较或声明完整预检通过。

## 实现与验证边界

浏览器操作使用经过 DSH 认证的固定 `/api/rp-studio/actions`，每个动作映射到一个固定 owner 方法；浏览器不能指定任意服务、agent、阶段或来源锚点。`capabilities` 只报告实际服务 API 与动作能力，不代替单次操作授权。完整内容只通过 owner 读接口，事件通知保留元数据范围。

当前正式正文优先读取 RP 最后一步的 storyHistory.records。narratives 继续作为规范来源与审计读取；未选版本只能在“旧版本审计”中明确展开。新事实尚无正文时显示等待写作。真实 DB 投影或规范版本信息表明故事需要有效 reader、但方法或依赖缺失时，界面保留状态和控制并明确报告 EFFECTIVE_HISTORY_UNAVAILABLE，不恢复旧正文。纯旧故事仍可按原 narratives 或已验证来源链阅读。Studio 不导入兄弟仓源码、不制造历史回执、不接管宿主 Agent 循环。

原生集成验收先固定每个已审 tgz 的 SHA256，以包含 SHA 的不可变文件名安装，并核对实际安装的宿主/客户端入口字节；同版本、同路径重新打包不能证明运行的是新代码。新准备脚本的接口检查与旧故事布局检查只记录真实已安装能力，不等同于完整 ST-B：最终七包闭环、冷重启与第二 home 恢复必须单独执行。[原生验收准备脚本](../scripts/native-integration/README.md)。

GM 绑定中的 profile 和 sources 是不可变开局来源；当前文风由 RP 最后一步负责，当前资料组合由 Database 的公开 effectiveV2 绑定负责。合法追加资料不会把初始来源列表变成另一份当前状态。存档保留精确的开局库、开局文风与资产默认版本，但这些被动依赖不能替换当前绑定；明确 sources:[]、profile:null 的故事恢复后仍保留该覆盖。dependencySummary 若存在，仅是记录的用途说明，不授权恢复或补齐依赖。若宿主已创建目标 Session、但创建归属尚未写入恢复日志就崩溃，匹配的头/前缀也不足以自动接管：保留冲突状态并报告 RESTORE_ID_CONFLICT，需明确处理归属或使用空目标环境，不承诺无条件自动续恢复。

导出或预检中的依赖用途按公开资料库/预设版本及“所选故事当前绑定”“资产默认来源”固定标签展示；旧存档没有该字段时显示未记录，不读取其他插件的私有 payload 推导。仅资产默认来源不表示历史从未使用；这些信息不改变 owner 的预检结论或恢复资格。

布局使用宿主右侧原生页签，可拉宽、全屏和窄窗口阅读。打开 owner 面板时核验实际客户端注册，仍保留各插件贡献的原生入口。发布前需分别记录旧故事回归、组件/适配器测试、打包安装，以及真实 tgz 的开局、采用、分支、重启和跨 home 恢复证据。
